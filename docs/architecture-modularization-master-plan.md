## 1. 目标与成功标准

最终目标是让 FAB-Agent 的能力能够分别开发、验证、交付和迁入公司内网，并通过稳定接口重新装配成完整应用。第一阶段交付形态是模块化单体；独立进程和服务按部署需求继续抽取。

一个模块达到“可分块迁移”，必须同时满足：

1. 有明确的输入、输出、依赖、错误语义和版本兼容要求。
2. 可以使用 Fake 依赖独立执行，并提供能看见实际效果的验收入口。
3. 在仓库外的干净目录运行，所有应用代码依赖来自显式交付物。
4. 可以接入内网适配器，调用方无需修改该模块内部代码。
5. 有集成验证、可辨识的失败状态和可以操作的回滚方法。

目录数量、ZIP 数量、Protocol 数量均不作为完成指标。主要指标是：替换依赖需要修改哪些模块、新增能力需要修改哪些模块，以及模块能否在独立环境验收。

## 3. 范围、约束和框架参考

### 3.1 本方案分成三类工作

| 类型 | 范围 | 完成口径 |
| --- | --- | --- |
| 等价解耦 | 契约、装配、Dispatcher、执行器职责、事件适配 | 既有外部行为保持，内部依赖可替换 |
| 新增产品能力 | Skill 管理、版本选择、Checkpoint、恢复 | 另有新功能用例、版本和启用门槛 |
| 迁移交付 | 离线包、模块演示、内网适配和组装验证 | 在目标环境逐块验收并留下版本记录 |

企业 SSO、真实系统调用、生产 ACL、多实例、分布式存储和服务化部署仍受对应企业任务约束。可先定义接口并用 Fake 验收；实际接入需要已有接口资料和环境条件。长期记忆与 Ragas 保持可选。

### 3.2 保留的行为约束

- 保留 `DecisionArbiter → Router → Playbook → ExecutionPlan → Evidence → Synthesis` 的业务语义和唯一会话决策权。
- Ready 的业务工具由服务端按计划执行；普通成功路径不增加模型选择工具的轮次。
- 保留只读限制、范围与时间语义、依赖失败传播、调用预算和停止规则。
- 保留证据校验先于制造结论正文输出、合法引用检查、局部修复和故障降级。
- 保留普通质量门零真实模型、零外网、零生产数据调用的约束。
- 目标模型执行链不提供 Text-to-SQL 或任意 SQL 执行能力。模型只选择获准的业务工具并提交结构化参数；查询由服务端受控实现。现有 SQL 工具的退出是明确的能力/Schema 变更，不伪装为等价重构，见第 5.9 节。
- 继续使用 Linux/WSL 开发约定，新增文档和脚本使用 LF；源码归档普通文件模式采用 `100644`。
- 便携包通过版本、显式文件清单、依赖和隔离验收交付，不新增 SHA-256 内容校验门。

### 3.3 参考框架的使用方式

| 参考方向 | 用于解决本项目的问题 | 应产出的本项目设计 |
| --- | --- | --- |
| OpenAI Agents SDK 的运行时分工思想 | Run/模型轮次/工具执行/事件之间的职责 | 轻量 Runtime、两类 Executor、明确的生命周期接口 |
| Pydantic AI 的契约与注入思想 | Schema、参数验证、Handler 和依赖漂移 | 统一工具契约、类型化 Ports、服务端执行上下文 |
| LangGraph 的状态与恢复思想 | 计划、状态更新和可恢复执行 | 显式执行状态、结果提交、Checkpoint 和恢复协议 |
| MS-Agent 的 Skill 管理思想 | 业务能力发现、加载、依赖和版本 | Catalog、Discovery、Loader 与可管理能力包 |
| 其他研究项目 | RAG、企业工作流、会话或适配器的专项问题 | 在具体任务中按需采用，避免扩大依赖面 |

这里使用用户材料提出的设计方向；不因参考某个框架而引入整个 SDK。确需采用新依赖时，在对应任务中固定版本并审查它的实际接口、离线安装条件和兼容性。

| 当前实现 | 目标归属 | 迁移原则 |
| --- | --- | --- |
| `agent_runtime/service.py` | Runtime 生命周期 | 保留公共入口，内部改为明确服务接口 |
| `agent_runtime/compatibility.py` | 兼容适配 + Bootstrap | 先迁装配职责；兼容访问和 patch 单独保留 |

| `agent_runtime/execution/` | Runtime 执行策略 | Ready 和 Loop 共享 Dispatcher，保留策略差异 |
| `agent_runtime/tools/` | Tools | 建立统一定义和执行治理后再做目录切换 |
| `intent_runtime/`、`planning_runtime/` | Orchestration | 保留已验证的类型和决策语义 |
| `manufacturing/playbooks.py` | Orchestration + Skill 引用 | 结构化规则保留唯一来源，不复制两套计划定义 |
| `model_gateway/` | Models | 保留现有流协议、目录与健康语义，补 Ports |
| `memory_system/context/` | Context | 保留可离线规则，先分接口后调整导入 |

| `personal_knowledge_runtime/` | Knowledge 个人知识用例 + 解析/存储/索引适配 | 用例与实现分离，owner 隔离、任务状态和删除语义逐项保留 |

| `manufacturing/seed.py` 与合成数据实现 | Simulation + 存储适配 | 模拟器不能成为真实数据 Provider 的隐式回退 |

领域内核的准入规则是：脱离 Agent、数据库、模型和当前请求，仍有独立业务意义。纯制造语义、词表和计算进入 `domain/manufacturing`，由 Tool、报表和离线评测共享；SQL、客户端、凭据解析、提示词和数据生成器不进入领域内核。首先约束依赖，目录改名在相应模块迁移时执行，不为改名启动全仓搬迁。

### 4.3 依赖规则

1. API 只调用应用服务，HTTP 类型不进入工具、编排和证据核心。
2. Bootstrap 可以知道接口及具体实现，负责绑定；纯核心不得反向导入 Bootstrap、API、`main.py` 或兼容装配层。
3. Runtime 通过 Ports 使用模型、工具调度、编排、上下文、存储和事件。证据用例可由阶段协调调用，通用 Loop 不导入制造证据内部实现。
4. Tool Handler 依赖领域逻辑与数据 Ports；外部客户端、SQL 方言和凭据解析位于 Integration/存储适配器。
5. Skill 引用已注册的工具、Workflow 和 Policy；内容不能提供执行身份、替换注册函数或绕过授权。
6. Evidence 消费规范化结果及其范围/来源，不依赖具体 SQL、模型供应商或 HTTP 响应。
7. Memory、Checkpoint 和 Trace 有不同用途与生命周期，允许共享存储设施，不共用一个含义模糊的状态对象。
8. 以上规则由显式依赖清单、AST 守卫、隔离导入和契约测试共同验证。

Skill/Workflow 发起受治理的业务查询或操作必须经过 Dispatcher；不得通过共享函数隐藏 I/O、绕过授权或执行预算。无 I/O 的制造语义、纯计算、计划构建与证据规则可由对应模块正常复用，不要求每个内部函数都成为模型可见 Tool。

### 4.4 逻辑模块与交付制品映射

逻辑模块、Python 导入包、分发制品和运行进程分别设计。模块可独立验收并允许显式依赖其他交付模块；独立验收不要求每个模块都是独立 Wheel、无依赖程序或服务。

| 制品组（拟议） | 包含内容 | 初期交付 | 独立发布条件 |
| --- | --- | --- | --- |
| 平台核心 | Runtime、工具框架、编排、模型服务、上下文/记忆用例、知识用例、Evidence、领域内核及必要契约 | 一个版本一致的源码 Bundle；可选一个平台 Wheel | 先整体发布，内部模块分别验收；按真实替换/维护需求再拆包 |
| 制造能力包 | 制造工具 Handler、Skill 资源、对应 Workflow 资源 | 按业务能力或部门组合 | 依赖平台契约，具备独立场景、版本和注册说明 |
| 企业/环境适配器 | 特定制造/搜索/身份或存储实现、模型 Provider 适配 | 按外部系统及平台依赖组合 | 接口稳定、依赖可离线安装、与应用实现单独更新有价值 |
| 演示与模拟夹具 | Simulation、Fake 响应及非生产数据 | 开发/验收可选包 | 与真实环境配置明确隔离，不是生产运行必需依赖 |
| 应用装配 | AgentDefinition、Bootstrap、API、前端、部署配置模板 | 一个 FAB Application Bundle | 固定兼容的平台/能力/适配器版本组合 |
| 小型公共契约包（可选） | 仅多个已独立发布制品共同消费的稳定值类型/接口 | 初期可随平台核心发布 | 出现真实跨包升级需求后再独立，不汇集所有领域契约 |

这些制品组可以合并成一次交付，不预先承诺固定 Wheel 数量。每份文件只有一个发布所有者。当前七个 ZIP 为各自隔离验收而重复包含 `app/__init__.py`、`app/manufacturing/__init__.py`、`app/manufacturing/processes.py` 和 `app/knowledge/__init__.py`；组合发布时必须采用版本一致 Bundle，或先解决共享文件所有权和命名空间。不得直接把这些 ZIP 转为多个互相覆盖 `app.*` 文件的 Wheel。

平台模块共同发布不代表导入一个功能就加载全部模块或依赖。包初始化保持轻量，不因 import 自动注册业务工具、读取 `.env`、打开数据库或创建客户端；OCR、真实模型传输等依赖通过对应 Adapter/可选依赖引入。独立演示必须覆盖导入过程，防止运行函数已注入 Fake、包初始化却仍绑定整个应用。

在 P0 的边界清单中确定首批制品范围和文件所有者，在试点 Dispatcher 成功后立即尝试仓库外安装；P5 按已验收的里程碑增量交付，不等待全部模块完成。

### 4.5 解耦的证明与否决条件

| 检查 | 必须得到的证据 | 未通过时的判断 |
| --- | --- | --- |
| 依赖方向 | Runtime 仅引用 Ports/契约，业务 Handler/SQL/HTTP 客户端由外部绑定；Import 检查通过 | 只是换目录，核心仍绑定具体实现 |
| 工具替换 | 同一工具分别绑定 Fake 和适配器，工具/Runtime 源码不改 | 数据访问与能力边界尚未解开 |
| 工具扩展 | 新增一个 Handler/Definition 并显式注册，Loop/Ready 不改 | 核心执行器仍硬编码业务能力 |
| 模型替换 | Fake/兼容供应商通过同一 Port 驱动运行，通用 Loop 不创建供应商客户端 | 模型传输仍渗入执行控制 |
| 存储替换 | 内存 Store 与测试持久化 Store 通过相同契约验收 | Memory/Checkpoint 用例仍绑定数据库 |
| 隔离运行 | 仅安装声明制品和依赖即可运行，不读取原仓库、原 `.env` 或演示库 | 交付仍含隐式宿主依赖 |
| 行为与性能 | 原有计划、预算、证据、引用、事件和模型调用数达到基线 | 解耦变更破坏已有业务保障 |
| 兼容收敛 | 旧入口消费者持续减少，新测试使用 Ports，退出证据可核对 | 兼容层正在成为新的长期耦合中心 |

本节描述验收目标，不代表当前项目已通过。交付报告必须分别列出：源码边界通过、模块隔离通过、Fake 装配通过和真实内网适配通过；不得合并称为“已完成解耦”。

## 5. 核心契约

### 5.1 ToolDefinition 与 ToolBinding

`ToolDefinition` 定义工具名称、契约版本、描述、输入模型/验证器、输出契约、只读/副作用属性和适用能力元数据。`ToolBinding` 将该定义与 Handler、执行策略和实际 Ports 绑定。模型只能看到公开输入 Schema。

公开 Schema 由输入契约导出，并通过导出适配器保持已有名称、默认值、必填项、枚举、描述和 `additionalProperties` 语义。Pydantic 可用于不可信边界；内部纯计算继续使用 dataclass 和 Protocol。严格类型、额外参数、空值、日期及数值转换必须明确，不能让默认类型强转静默改变旧工具行为。

新增执行前验证可能拒绝旧 Handler 曾意外接受的输入。这类变化需要逐工具列出反例、预期错误和契约版本，作为明确的验证增强验收，不能混写为完全等价。既有合法输入与正常结果优先保持兼容。

现有 `TOOLS` 列表与 `TOOL_HANDLERS` 字典先保留为兼容视图，维持对象身份及当前测试依赖的实时 patch 行为。旧入口返回的 Handler 结果仍保持所需对象身份。新旧接口通过单向适配衔接，避免两份独立权威注册表。

试点期间允许显式的 LegacyBindingAdapter 承接尚未迁移的工具，Definition/Binding 标明契约模式，由同一个 Registry 和 Dispatcher 调度。新执行失败不能再调用旧 Handler 重试；不得在 Ready/Loop 中散布按工具名称选择新旧实现的分支。兼容视图按第 10 节的消费者清单逐项退出，新功能测试直接注入 Port。

`submit_analysis` 属于答案提交协议，保留独立校验和综合路径，不因工具统一而作为普通业务 Handler 执行。

### 5.2 ToolExecutionContext

包含服务端提供的主体、`run_id`、调用标识、计划步骤、预算/截止时间、取消信号和需要的数据 Ports。模型参数中不包含可改写的可信身份、角色和授权范围。

Runtime 创建运行作用域；具体工具只获得自己需要的依赖。Context 不向所有 Handler 暴露一个包含数据库、模型客户端和全局配置的服务字典。

演示身份映射继续走演示策略。生产身份必须通过受信任 Adapter，Policy 的允许结果才具有生产授权意义。Fake Policy 可以验证拒绝语义，不等于完成 SSO/RBAC/ACL。

### 5.3 ToolResult 与结果归约

建议内部结果至少包含：调用 ID、工具名、工具版本、状态、数据或受控结果引用、结构化错误、来源/范围、行数、耗时。状态采用明确枚举，例如 `succeeded`、`invalid_arguments`、`denied`、`blocked`、`failed`、`timed_out`、`cancelled`。

- 错误模型区分解析失败、参数不合法、授权拒绝、预算阻断、数据源故障和内部异常，并明确能否重试。
- 错误信息面向调用方脱敏；完整异常按现有审计策略处理。
- Evidence 适配器把结果转换成现有 `EvidenceObservation` 与调用级来源，保持范围、时间、粒度和引用身份。
- Runtime Reducer 负责更新消息、来源、证据和使用量；Handler 不直接修改这些共享容器。
- 大结果使用受访问控制的引用和必要摘要；不把整份结果重复塞入模型上下文和 Checkpoint。
- 外部 API、Trace 和旧结果读取通过适配器保持现有 `ok/success/blocked/error` 等协议；内部枚举统一不等于立即改写所有公开状态码。
- `timed_out` 表示调用方停止等待，不能自动表示底层同步任务或外部操作已经取消。执行状态及审计要区分已确认取消与结果未确定；超时/取消后的迟到结果不得擅自更新已结束的 Run。

### 5.4 Dispatcher 与 Policy

公共调用流程：解析/验证输入 → 检查工具可用性 → 检查主体与数据范围 → 检查预算/期限/取消 → 执行 → 验证输出 → 记录结果与事件。

策略检查不得触发实际业务查询。禁止调用时，Handler 调用计数必须为零。未知工具、缺失绑定和未知适配器均明确失败；生产来源失败不得静默退回演示数据。

Ready、Loop 和知识预取复用公共执行服务。计划依赖阻断、模型消息格式以及各路径特有的行数限制，通过策略参数和调用方适配明确保留，不强行抹平原有差异。预算由单一所有者记账，避免 Dispatcher 与旧 LoopGuard 各扣一次。

| Policy 类别 | 所有者及强制位置 | 示例 |
| --- | --- | --- |
| Runtime Policy | Runtime 管理预算/期限/取消/重试状态，Dispatcher 使用同一决策和记账接口 | 工具次数、重复调用、模型轮次、超时及停止 |
| Business Authorization Policy | 服务端授权接口提供判定；Dispatcher 检查调用资格，数据 Provider 在查询/召回处执行范围限制 | 厂区/租户/用户/密级与操作资格 |
| Evidence Policy | Evidence 用例独立检查，结果由综合阶段强制使用 | 范围/时间/grain 一致性、必需证据与结论强度 |

授权通过不代表证据足够；Dispatcher 的授权检查也不能代替 Provider 的行级/来源 ACL。三类 Policy 不集中成一个了解全部制造逻辑的通用引擎。模型重试、工具重试分别定义；只有具备相应幂等语义的调用才允许自动重试。

### 5.5 Runtime、模型与事件 Ports

| Port/对象 | 主要职责 |
| --- | --- |
| `AgentRunRequest` / `RunResult` | 运行输入和最终输出；与旧字典之间有适配 |
| `ModelGatewayPort` | 模型请求、流事件、工具调用、Usage、取消与供应商错误 |
| `ToolDispatcherPort` | 接收规范化调用和服务端 Context，返回 ToolResult |
| `PlanningPort` | 接收已确认任务与约束，返回 ExecutionPlan |
| `EvidencePort` | 消费计划和结果，输出验证及答案契约 |
| `EventSink` | 接收版本化运行事件；适配现有审计和 UI 进度 |
| `RunState` / `StageResult` | 运行内唯一事实及阶段产出，不建立相互漂移的副本 |
| `SessionStorePort` | 会话记录读取和写入，沿用租户/用户隔离 |
| `CheckpointStorePort` | 保存可恢复状态及结果提交关联，后续阶段实现 |

现有 `CoordinatorStateView` 可作为过渡。先把高频跨模块字段类型化，再用明确的阶段结果替换动态字段访问；不一次性拆成多个相互同步的可变状态对象。

### 5.6 Skill、Workflow 与 Evidence Policy

Skill Manifest 至少声明：ID、版本、说明、状态、适用制程、输入要求、工具依赖及版本范围、执行模式、Workflow 引用、Evidence Policy 引用和内容资源清单。

Skill 包可包含 `SKILL.md`、Manifest、Workflow 引用、参考资料和验收场景。Workflow 可以先引用既有 Playbook/Plan Builder；避免 YAML 与 Python 各维护一套同名业务规则。

Catalog 验证依赖和发布状态，Discovery 根据已确认意图/范围筛选，Loader 只加载所需内容。默认路径不为选择 Skill 新增模型请求。复杂组合能力在单 Skill 验收后单独扩展。

Run 固定所选 Skill、Workflow、Policy 的声明版本；发布新版只影响新 Run。版本固定不自动改变旧 Handler 注册表的 patch 兼容语义，二者必须分开验收。Skill 资源按显式清单及安全相对路径加载，不执行任意上传代码或隐式导入插件。

### 5.7 AgentDefinition 与其他定义的边界

| 对象 | 应定义的内容 | 不承担的职责 |
| --- | --- | --- |
| AgentDefinition | 助手角色、模型选择策略、可用能力范围、默认策略引用和契约版本 | 不存 Run 可变状态，不持有全部服务客户端，不自行授予用户权限 |
| SkillDefinition | 专业能力说明、输入要求、依赖、执行模式及资源版本 | 不自建 Loop，不绕过 Dispatcher |
| ToolDefinition | 原子操作的输入输出、描述、版本及执行属性 | 不读取配置或根据模型参数制造可信身份 |
| WorkflowDefinition | 结构化步骤、依赖和必需证据引用 | 不与 Playbook/Plan Builder 重复维护同一业务规则 |
| PolicyDefinition | 某一类别强制约束的声明和版本 | 声明本身不等于已经执行授权或证据检查 |

同一个 Skill 可被不同 AgentDefinition 引用，可用能力范围还必须与服务端主体权限取交集。初期只有一个 FAB AgentDefinition 即可，不为这些契约引入 Handoff 或多 Agent 协作系统。

### 5.8 状态推进、提交与事件的权责

Runtime 是运行状态的唯一推进者；Reducer 将 ToolResult/模型结果转换成显式更新。Handler 和 Adapter 只返回结果及必要元信息，不直接修改消息、来源、步骤状态或 Checkpoint。

| 职责 | 所有者 | 明确的提交语义 |
| --- | --- | --- |
| 运行内状态与预算 | Runtime/Reducer | 更新按调用 ID/尝试 ID 关联，不重复应用同一已确认结果 |
| 可恢复状态提交 | Runtime 提交协调器，经 Store Port 调用 | 提交包含期望状态版本、步骤更新和结果引用；冲突/失败返回明确错误 |
| 持久化 | Checkpoint/Result Store Adapter | 保证契约承诺的事务边界，不能自行决定恢复或宣告成功 |
| 执行记录 | 提交协调器和存储适配器 | 已提交状态关联可读取结果与单调序号，可据此重建 |
| UI 进度、指标、审计输出 | EventSink/Observability Adapter | 事件带状态版本/调用标识；区分提交前通知与提交后事实 |

P4 明确区分未执行、可能执行但未提交、结果已提交三类情况。执行恢复以已提交状态与结果为依据，不以 UI 进度或日志为真值。跨结果存储与 Checkpoint 无共同事务时，先持久化结果再提交引用，并检查引用可读性和孤立结果清理；不得假定跨系统原子性。

对恢复必需的执行记录，应纳入同一存储事务或可重放提交机制；普通展示/指标事件允许按已提交状态重建。不要求所有遥测与数据库进行分布式事务，也不因此引入消息队列。P4 不承诺任意外部副作用恰好执行一次。

### 5.9 数据访问职责与无 SQL 模型边界

#### 5.9.1 接口由消费方定义，实现由接入侧提供

| 部分 | 职责 | 不承担的职责 |
| --- | --- | --- |
| 业务 Data Port | 由工具/知识用例等消费方定义需要的数据、范围、DTO 与错误语义；共享稳定契约可随平台交付 | 不暴露连接、表名、SQL、驱动游标；不依赖具体 Integration |
| Repository / 查询实现 | 实现业务 Port，持有固定查询、受控查询构造、范围过滤、分页及 DTO 映射 | 不从模型文本获取可执行 SQL，不自行授予身份权限 |
| 技术 Adapter | 封装必要的数据库方言、驱动或协议差异 | 不成为所有业务共用的任意 SQL 执行入口 |
| 连接设施 | 按需管理客户端/连接池的获取、释放、超时、生命周期及凭据引用 | 不承载业务查询，不让模型选择连接串、账号或任意数据源 |

Repository 与技术 Adapter 是职责划分，不要求每次调用经过四个独立类；初期可由一个 SQLite Repository 直接实现 Data Port。不得为了目录对称而创建空转发层。Connection Manager 只有在真实接入与复用需求出现时才扩展，优先复用驱动已有连接管理能力。

现有 `EnterpriseDataProvider` 的 manifest/summary/page 接缝不覆盖全部报表工具；`manufacturing/reports.py` 仍有直接 SQL。按试点工具逐项抽出所需 Port，而不是创建一个接收任意查询文本的万能 Data Port。

DTO 明确范围、单位、时间边界、grain、统计口径、精度/空值、来源和新鲜度；数据源失败与合法空结果必须区分。允许 Repository/Adapter 做等价聚合下推，不为分层将全部明细搬回 Python。现有 Cpk 的 SQL 聚合迁移须核对标准差、规格限、分组和舍入语义，不能因实现语言变化悄悄改变结论。

#### 5.9.2 面向量化小模型的强制约束

目标链路为：`模型选择业务工具/填写参数 → Dispatcher 验证 → Handler → 业务 Data Port → 受控查询实现 → 数据源`。Ready 路径仍由服务端按计划调度，无需模型选择业务工具。

- 不向模型提供 SQL 执行、SQL 生成后执行、数据库控制台或同等通用能力；不得用“换一个大模型写 SQL”作为失败回退。
- 工具输入只接收明确的业务参数，例如设备、制程、日期、指标枚举及有界行数；不接收 `sql`、SQL 片段、任意表/列名、表达式、连接串或可绕过验证的查询 DSL。排序等可变项由服务端枚举映射到固定实现。
- SQL、参数绑定和受控查询构造留在 Repository/Adapter。值使用参数绑定；不可参数化的标识符由服务端白名单映射，不拼接模型文本。授权主体、租户范围及数据源路由由可信上下文提供，不能由模型改写。
- 未知工具、额外参数、越界范围、无权限或缺失能力均在执行前明确拒绝；不得静默放宽过滤、切换模拟来源或追加模型请求来编写 SQL。信息不足时澄清；能力不足时明确说明限制。
- 隐藏 Schema 不足以封住入口：即使模型伪造旧工具名/调用参数，Dispatcher 与 Binding 的允许能力检查也须阻断，受控查询执行计数为零。
- 提示词、Skill 文本及模型是否遵从仅作辅助，不是执行安全边界。用户输入或检索内容中出现 SQL 字符串，也不能自动成为可执行指令；这不等于禁止在说明性文本中讨论 SQL。

#### 5.9.3 旧 SQL 工具的迁移与验收

当前 `query_manufacturing_data(sql)` 仍绑定 `manufacturing/reports.py:safe_select`，尚未禁用。其 SELECT/表白名单与只读限制不能替代上述目标边界，亦不构成生产接入资格。

在 `MOD-003` 登记其定义、调用方、模型暴露点和退出条件；`MOD-004～007` 建立无 SQL 的工具契约与服务端能力限制；`MOD-008` 按实际业务用例用具名结构化工具覆盖所需能力，并从目标模型工具清单和可执行绑定中移除旧 SQL 能力。不要求另建同名万能替代工具，也不保留可由模型开启的 SQL 后门。`MOD-009/015` 验证替代工具、双执行路径及兼容台账；迁移未完成时不得宣称已满足无 SQL 目标。

这是用户确认的能力收缩，需列明旧调用的替代方式、拒绝结果及 Schema/能力版本变化。历史 P0 契约和受控离线回放保留用于溯源；先记录差异、评审消费者迁移，再建立对应的新基线，不自动刷新旧快照掩盖变化，不将旧 SQL 工具作为运行失败回退。真实内网 Profile 不得绑定该旧能力。

#### 5.9.4 数据库与报表/API 两类接入

用户已确认可能获得只读账号或报表接口，目前不固定具体接入方式。上层先定义业务 Data Port；D0 用 Fake/SQLite 完成切片，真实条件明确后按需实现数据库或报表/API Adapter，不要求两套同时开发，不为尚不明确的接口预建空实现。

```text
业务 Tool → 业务 Data Port
                ├── Fake / SQLite：当前开发与隔离验收
                ├── 只读数据库实现：获准的固定查询/受控查询构造
                └── 报表 / API 实现：获准的接口调用、字段和口径转换
```

三类实现是可选择的绑定，不是默认依次尝试的回退链。可按业务能力混合来源，例如设备状态走 API、测量统计走只读数据库；绑定由 Bootstrap/Profile 根据可信配置确定。模型不选择连接串、任意数据库或任意接口 URL。来源故障不自动换库、换报表或换成模拟数据；确需来源切换须另有显式策略、授权及语义验收。

| 接入方式 | 接入实现负责 | 特有验收 |
| --- | --- | --- |
| 只读数据库 | 固定查询、参数绑定、可信范围过滤、只读凭据引用、连接获取/释放、查询超时和结果转换 | 仅访问获准对象；拒绝任意 SQL；连接失败、慢查询和资源释放可辨识；只读账号不等于允许任意读 |
| 报表 / API | 固定接口/报表与业务参数映射、认证、分页、字段/单位转换、刷新时间和错误转换 | 响应格式变化、缺字段、分页失败、陈旧数据、超时与权限反例；模型不能提交任意报表表达式或接口地址 |

同一业务 Port 的实现须满足相同业务口径，而非强求原始响应相同。契约明确必需与可选字段；只有 Cpk 数值而缺少场景所需样本量/范围的报表，不能默认通过完整证据验收。缺少必要数据或无法证明统计口径时，明确标记该能力不可用或证据不足；不补造字段，不静默降低契约来适配来源。

同一分析需要多个来源时，按明确设备/批次标识、单位、时间范围和新鲜度规则组合，保留各自血缘；不能假设不同系统是同一快照，也不预建通用跨库 SQL 引擎或分布式事务系统。具体组合能力按业务场景另验收。

### 5.10 应用存储与现有 database.py 的渐进处理

业务数据读取采用 `Agent / Skill / Workflow → Dispatcher → Tool → Data Port → 接入实现`；会话、执行记录、个人知识/索引、模型配置等内部存取采用 `应用服务 → Store / Repository Port → 存储实现`。后者不伪装成模型工具。制造来源迁移不要求同时迁移会话库，应用存储替换也不应改变业务工具契约。

| 数据归属 | 本项目负责 | 本项目不默认执行 |
| --- | --- | --- |
| 公司业务数据库/报表系统 | 按获准范围读取、转换、记录来源与错误 | 建表、Schema 升级、写入生产事实、生成模拟记录或擅自改变源系统配置 |
| 应用自有存储 | 显式初始化、Schema 升级、备份/恢复及会话等业务存取；数据路径与安装路径分离 | 因替换制造来源而重建或清空用户数据；将内部写入权限交给模型 |
| 演示数据与 Fake | 独立的模拟夹具和初始化流程，明确标注非生产来源 | 成为公司接入的必需依赖，或在真实来源故障时隐式启用 |

现有 `persistence/database.py` 集中连接、初始化、迁移等职责；普通 `connect()` 会挂载多个部门 SQLite 库并建立兼容视图，缺库时可能触发初始化。物理分库不等于访问依赖已经解耦，不能以此宣称单模块可独立搬迁。

处理顺序如下；它是现有 `MOD-*` 的补充验收要求，不新增一轮全仓数据库重构：

1. `MOD-003` 登记业务查询与内部存储消费者、所需库/表、跨库依赖及初始化副作用，明确文件/数据所有者和未退出的兼容入口。
2. `MOD-005～007` 的单工具切片抽出所需 Port 和 Fake/SQLite 实现；新查询路径只获取所需资源，不因单工具运行而挂载或初始化全部数据库；在仓库外缺少其他库时也可验收。
3. `MOD-008/009` 分批迁移其余业务工具，验证独立运行及替换来源无需修改工具核心/Runtime，保留统计与来源语义。未迁移的访问明确留在台账，不伪称统一入口已经退出。
4. `MOD-011/015` 明确 Runtime 所需 Store 接口与装配；会话、知识等现有存储实现可暂作为 Adapter 保留。按对应模块迁移消费者后，再收缩全库挂载、兼容视图和全局连接入口，不要求在 015 强制删除全部旧数据库实现。
5. 稳定边界下，初始化、Schema 升级和模拟生成由显式部署/维护入口负责，普通业务查询不触发全局建库/迁移。旧消费者未退出前保留经审查的兼容行为，结合 `MOD-025～028` 逐块验证装配和目标环境运行。

保留现有数据、表和历史迁移记录，不为目录重构立即更换数据库引擎或搬动文件。持久化变更必须提供兼容读取、备份与回退说明，另获所需实施授权。企业连接管理按第 9.3 节实际需要扩展；一个 Tool 不等于一个数据库、一个连接池或一个独立服务。

### P5：模块交付与内网集成

## 7. 每模块可查看的验收结果

每个模块提供以下四项：一份职责/契约说明、一套固定输入及可读结果、一条独立运行命令、一份含失败场景的验收报告。可读结果使用结构化文本或 JSON；只有业务确实需要时增加独立预览页，不先建设通用管理平台。

| 模块 | 最小演示 | 必测反例/故障 | 迁移完成的证据 |
| --- | --- | --- | --- |
| Agent/装配 | 加载一份 AgentDefinition，列出实际绑定 | 缺 Port、未知版本、缺 Skill | 仅改绑定即可切换 Fake 与目标适配器 |
| Tools | 输入设备范围，返回规范化结果 | 错参、未知工具、拒绝、超时 | 不加载 Runtime 也可验证工具 |
| Runtime | Fake 模型返回工具调用和最终提交 | 重复调用、预算耗尽、取消、坏响应 | Ready/Loop 公共执行策略一致 |
| Orchestration | 问题转换为路由、Playbook 和计划 | 缺范围、冲突输入、未知/循环依赖 | Golden Set 和计划语义保持 |
| Skill | 列出能力、选择并加载一个 Skill | 禁用、缺工具、版本不兼容 | 无需改 Runtime 即可增删能力 |
| Models | Mock SSE、工具调用和 Usage | 断流、坏 JSON、重试和熔断 | 无真实端点可验证协议与健康交互 |
| Context | 历史输入转换为受限上下文 | 超预算、无关历史、歧义追问 | 不依赖全应用或长期记忆 |
| Memory | 按主体读取/写入会话 | 不同租户/用户、删除与缺失 | 不泄漏其他主体数据；存储可替换 |
| Evidence | 固定工具结果转换为声明状态 | 错范围、错时间、错误引用、背景充主证据 | 合法事实保留，越界结论被限制 |
| Observability | 收集一个 Fake Run 的事件报告 | 乱序、缺事件、异常结束和脱敏 | 可关联 Run/Step/Source；旧 UI 仍可消费 |
| Integrations | 对脱敏响应执行 DTO 映射 | 字段缺失、分页、超时、来源故障 | 明确数据范围和血缘，故障不回退越权来源 |
| API | 装配通过验收的模块，运行用户链路 | 错误码、流式中断、会话隔离 | 请求/响应、事件和数据隔离符合基线 |
| Checkpoint | 中断与恢复步骤演示 | 不确定提交、旧版本、过期结果 | 正确继续或明确拒绝恢复 |

建议报告字段：`module_id`、模块/契约版本、基线提交或本地构建 ID、执行环境、绑定实现、场景结果、关键计数、性能、已知边界。只记录必要元信息，避免携带真实数据、凭据或完整敏感请求。

### 7.1 数据接入与无 SQL 边界的验收补充

1. 同一业务工具替换 Fake 与 SQLite/受控 Adapter，Handler/Runtime 源码不改；输出契约、范围、单位、统计口径及来源语义一致。
2. 目标模型工具清单不包含 `query_manufacturing_data(sql)` 或等价通用 SQL 工具，业务参数 Schema 不接受任意查询文本、连接信息和未声明参数；不能仅凭提示词声称通过。
3. Ready、Loop 及适用的 Workflow 调用统一走受控入口；伪造旧工具名、额外 `sql` 参数、非法标识符、越权范围或未知数据源时明确拒绝。权限/参数拒绝时 Handler 与查询执行计数均为零；工具内部受控校验失败时至少保证查询计数为零。
4. 覆盖数据源不可用、超时、字段/单位不匹配、分页错误和合法空结果；错误不得伪装空数据或静默回退演示库。超时后迟到结果不得更新已结束的 Run；是否已取消底层查询单独说明。
5. SQL 工具退出报告单列旧用例对应的新业务工具、能力/Schema 版本、消费者迁移与拒绝行为；旧快照不自动更新，未覆盖的业务能力明确报告缺失。
6. 单工具隔离演示在无其余部门库、无原仓库 `.env`、无全局建库过程时可运行；公司接入配置不触发本地模拟库初始化，不对公司业务库执行 Schema 或 seed 操作。
7. 对同一 Port 使用数据库式响应夹具和报表/API 式响应夹具，验证字段、单位、范围、统计口径和错误转换；这是接入契约测试，不要求当前实现两套真实 Adapter。实际采用哪一种，再追加其目标环境证据。
8. 来源绑定写入验收报告；故障不自动换来源。来源缺必要字段或统计口径不兼容时明确能力不可用/证据不足，不能以零值、模拟值或删除字段悄悄通过契约。

以上可用 Fake 模型和受控夹具验证服务端边界，不证明量化小模型已能正确选择工具/填写参数。目标模型可用后，工具选择、错参、缺信息澄清和多步骤稳定性另按实际模型版本及已有授权验收；本轮不自动启动真实模型或 Live 门。

## 8. 行为、测试和性能门槛

### 8.1 分层验证

1. 每任务只跑与变更有关的契约、边界与故障测试；不为简单转发函数机械复制测试。
2. P0、P1/P2 等关键阶段结束，以及 Schema/API/认证/流式/证据等重大边界变化，执行既有完整离线质量门。
3. 保留 Playbook、RAG、Ready Execution 和 Trace Replay 的固定场景；用户暂缓的真实 Live 门不因本文自动重启。
4. 目标模块在仓库外解压/安装后验收，移除仓库 `PYTHONPATH` 影响，并检查应用导入来源。
5. 数据适配器先用脱敏夹具。开发机不直连生产 Oracle；生产接口细节由实际资料决定。

### 8.2 必须保持的业务不变量

- 固定 Ready 场景的业务工具选择模型调用数始终为零。
- 同一允许调用的来源/身份检查不因入口是 Ready、Loop 或检索预取而消失。
- Handler 被拒绝前无业务调用；循环预算由同一个记账结果驱动。
- 依赖失败的下游步骤不伪装成功；证据失败不因切换 Executor 而升级结论。
- 综合局部修复最多按既有预算执行，不重跑业务工具、不重复最终正文。
- 同一来源 ID 的含义稳定，Scope、时间、grain 与调用级引用持续可追踪。
- 普通成功路径不增加未登记的模型请求；新 Skill 默认选择不增加模型轮次。
- 旧 API/Trace/前端契约变化必须单独说明并版本化，不能自动刷新快照掩盖差异。
- 无 SQL 模型边界按第 5.9 节单独验收；任意查询文本不因模型输出、Skill 内容或检索结果而进入执行器。旧 SQL 工具退出属于已明确的能力收缩，不冒充旧工具清单完全不变。

### 8.3 性能比较方法

当前 P0 正式验收采用用户批准的同轮 reference/current 配对协议，详见 `evaluations/mod_002_paired_protocol_v1.json` 和 [MOD-002 报告](reports/mod-002-behavior-baseline.md)：默认每场景每版本 1000×2 样本、每批 10 warmup、50 样本 AB/BA 块；固定保留 v4 相对容差，墙钟 median/p95 是硬门，CPU/cleanup 仅诊断。2026-10-24 两次预声明 A/B 已通过，历史静态绝对上限失败不改写为通过。共享 harness 在执行前固定原行为 v2 的业务路由日期 2026-08-07 与历史捕获环境日期 2026-10-22，禁止通过输出归一化隐藏日期/计划差异；冻结 ZIP 与行为 v2 不改。该结果不是生产 SLO 或全部 WSL 噪声已消除的证明。下文通用分层原则不替代已冻结的具体正式协议。

P0 使用固定数据、Fake 延迟、模型响应、机器和 Python 环境，区分首次加载与预热后运行。日常回归预热至少 10 次后采样至少 30 次，以中位数和离散程度观察趋势；阶段性 p95 验收使用至少 100 次、优先 200 次离线样本，并记录分位数计算方法和独立批次结果。30 次样本的尾部统计只作观察，不作稳定 p95 的证明；样本数增加也不等于已经证明生产 SLO。

分开测量以下层级，P0 在实际分布和测量噪声已知后冻结各自的数值门槛：

| 层级 | 测量对象 | 门槛制定方式 |
| --- | --- | --- |
| Dispatcher 微基准 | 同一 Fake Handler 直接调用与经过完整公共治理调用的配对差值 | 为新增开销单独规定绝对上限及测量噪声，不用整个 Runtime 的容差覆盖 |
| 完整 Runtime | 固定响应、数据和延迟下的 Ready/Loop，全程保留 Policy 和事件路径 | 按场景冻结中位数/p95 回归容差，短耗时与长耗时场景分别制定 |
| 真实数据接入 | 连接获取/等待、受控查询、网络/分页、DTO 转换和返回规模 | 在获准的目标环境按来源及业务场景单独制定；Fake/SQLite 热 Runtime 数字不充当真实数据库性能证明 |
| 提示词及模型请求 | 同一成功/故障场景的请求次数、输入 Token 和提交修复次数 | 请求次数按契约精确检查；Token/长度变化单独解释 |
| 真实模型端到端 | 实际端点的首片、用户首答、工具阶段和总耗时 | 仅在既有授权 Live 环境测量，供应商噪声与本地开销分开 |

以下是可以立即固定的行为门，而非尚未测量的延迟数值：

| 指标 | 验收约束 |
| --- | --- |
| Ready 模型选业务工具次数 | 精确为 0 |
| 等价成功场景模型请求数 | 不超过基线；失败修复仍受原有预算约束 |
| 等价成功场景输入 Token/提示词长度 | 原则保持；增加超过 5% 必须明确用途和评审 |
| 工具有效调用/失败分类 | 固定场景与基线一致，新增拒绝用例单独统计 |
| 证据/引用质量 | 不退化；不得用更多降级或空结果换取通过 |

v1.0 中统一采用 `max(相对回归, 固定毫秒增量)` 的延迟公式撤回；短耗时模块不能获得足以掩盖数倍回归的固定余量。每项数值门在改造前冻结，失败后不能为通过测试而临时放宽。

记录采样数、时钟、测量粒度、夹具、解释器、机器与冷/热状态。Token 统计区分真实 tokenizer 和离线长度代理，不能把代理值当实际计费。用户可见首个最终答案增量、模型 API 首片、工具耗时与总耗时分别记录。增加采样主要针对廉价的离线测试，不要求新增真实模型调用或启用用户暂缓的 Live 门。

## 9. 内网分块搬迁路线

开发顺序与搬迁顺序不同：开发优先修复 Tools/Runtime 的边界；搬迁先引入最少外部依赖的契约和规则，再接适配器和应用。

| 批次 | 搬迁内容 | 公司侧前提 | 当批可见效果 |
| --- | --- | --- | --- |
| M0 | 项目环境、离线依赖、模块清单和固定夹具 | Python 版本及依赖安装条件确认 | 干净环境可重复执行验收命令 |
| M1 | 身份/数据/工具契约、纯决策、排序、证据与上下文规则 | M0 | 输入场景得到计划、排序及证据判断 |
| M2 | 工具系统与 Fake/演示数据适配器 | M1 | 不加载模型即可查询、拒绝错参并查看 ToolResult |
| M3 | Model Gateway、Runtime 与显式装配 | M2 | Fake 模型下完整 Ready/Loop，随后替换已批准模型端点 |
| M4 | Skill 包与内网制造/知识适配器 | 稳定 Tools/Ports；实际接口资料和可信身份条件 | 按业务能力验收，区分模拟与真实来源 |
| M5 | API、会话/个人知识存储、前端与审计集成 | 前序模块兼容；目标存储与访问条件确认 | 用户端完整链路、来源导航和权限反例 |
| M6 | Checkpoint/恢复及后续服务化 | 恢复阶段通过；相应部署条件具备 | 故障后继续执行；独立部署另行验收 |

公司侧暂无真实接口时，批次仍可用明确标注的 Fake/演示 Profile 验收模块装配。不能因此宣称真实制造数据、生产 ACL 或 Oracle 接入已完成。

每个交付包包含源码或 wheel、版本/依赖清单、验收夹具、离线演示说明和兼容信息。依赖预装或通过离线 wheelhouse 提供；验收过程中不隐式访问公网。`model_transport` 当前需要目标环境安装清单声明的 `httpx`。

模块安装路径与运行数据路径分开，包升级不覆盖用户数据、知识文件、日志或密钥。接入清单记录模块版本组合和目标环境，不使用内容哈希作为搬迁验收条件。

### 9.1 环境与依赖锁定

- `requirements.txt` 中的兼容范围用于开发约束；每次实际交付另记录目标环境解析出的直接和传递依赖精确版本。
- 记录 OS、发行版/基础运行库、CPU 架构、Python 版本/ABI、CPU/GPU 运行模式及模块可选依赖。Linux/WSL 构建成功不等于 Windows 或其他架构可安装。
- 纯 Python 和二进制 Wheel 分别识别。OCR、ONNX Runtime、图像/PDF 处理等按目标平台准备 wheelhouse，并在匹配的干净环境验证安装、导入和固定样例。
- 依赖按制品/能力声明；不使用 OCR 的工具或 Runtime 验收，不强制安装整个 OCR 依赖集合。
- 平台不匹配、缺包或版本冲突在预检时明确失败；不隐式联网补包、换版本或换 Provider。不同目标环境分别维护解析结果，不能伪称一个锁文件适配所有平台。

### 9.2 交付来源与验证范围

交付记录包含发布版本、源提交或本地构建 ID、构建方式、平台、文件清单、文件所有者、依赖及验收结果。发布清单/隔离测试能验证声明与可运行性，不能据此证明内容完全未被修改。

遵循用户要求，不新增 SHA-256 或其他自建内容哈希门，也不把哈希作为这次内网迁移的前置条件。公司已有的受控分发/制品库流程按其既定方式记录，本文不新增或绕过其验证机制；如以后需要改变本项目的校验要求，应作为独立范围处理。

### 9.3 Data Access 接入成熟度

下表是数据接入的能力层级，不是新的串行任务或必须一次建成的平台；不改变 P0～P5 顺序，不自动激活企业接入任务。各级均遵守模型无 SQL 边界。

| 层级 | 必需能力与验收 | 暂不要求 |
| --- | --- | --- |
| D0：Agent 验证 | 消费方 Data Port、Fake/SQLite、DTO/错误/来源、结构化业务参数；固定成功和拒绝场景，替换 Adapter 不改调用方 | 真实数据库、统一数据源注册平台、生产连接池 |
| D1：少量真实来源试点 | 获准的固定查询/受控实现、可信范围、只读账号、凭据隔离、参数绑定、必要连接复用/释放、查询超时及故障反例；脱敏夹具与实际环境分别验收 | 企业级统一连接平台、跨库 SQL 引擎、提前接入全部部门 |
| D2：多部门接入 | 按实际来源配置注册及版本，管理多个池/客户端、资源限额和生命周期，按 MES/FDC/SPC 等真实边界组织查询实现；未知来源拒绝、不跨主体复用权限 | 自建通用数据库驱动层、任意跨库查询、强制服务化 |
| D3：长期运营 | 数据源健康、凭据轮换、配置治理、监控、兼容与变更/回滚流程，均有实际运维验收 | 没有需求支撑的复杂服务化或通用数据中台 |

D0 不能以“先用 Fake”为由省略数据契约；D1 不能以“连接管理以后再做”为由省略资源释放和最小安全约束。配置、凭据与来源路由由服务端装配决定，模型不持有连接、不选择任意数据库。真实来源失败不静默切换到模拟数据。

连接设施优先复用成熟驱动能力，SQLite 不必仿照远程数据库先建统一连接池；没有跨来源复用需求时，不单独建设 Connection Manager 系统。少量真实数据试点须先满足实际接口与授权条件，不以文档中的成熟度层级视为已获企业接入授权。

### 9.4 公司侧接入确认与绑定记录

当前仅确认两种接入方式均有可能，不代表具体账号、接口资料、网络环境或生产授权已具备。每项能力接入前逐项确认以下资料；不能用“已有只读账号”替代实际范围与口径验收。

| 确认项 | 需要确定的内容 |
| --- | --- |
| 业务能力与 Port | 支撑哪个工具、契约版本、必需字段、时间/单位/统计口径及数据不足策略 |
| 来源与标识映射 | 实际来源、可访问对象或固定报表/API、设备/批次标识对应关系、时间区/时间边界及刷新时间 |
| 权限与凭据 | 受信任主体、可读范围、认证方式、凭据外部保存及引用方式；不在交付文档或模型上下文中存放凭据值 |
| 连接或接口约束 | 获准的网络路径、驱动/协议、超时、分页、行数/频率/并发限制及资源释放 |
| 实际验收 | 脱敏样例、允许/拒绝用例、来源故障和旧结果对照；记录尚未满足的条件 |
| 显式绑定与回退 | 能力/Port → Adapter 及版本 → 来源配置引用；切换需审查，故障不自动换来源；保留可恢复的旧装配配置 |

先为首个实际来源保存最小绑定配置与接入说明；不因这份清单建设通用数据源管理平台。多个业务工具可复用一个受控接入实现；同一分析也可在明确规则下组合数据库与 API 来源。实际查询范围和结果来源须可审计，但不把连接信息或敏感原始响应泄露给模型或前端。

## 10. 版本、兼容与回滚

- 契约、模块实现、Skill/Workflow/Policy 和持久化 Schema 分别标识版本；兼容关系显式声明，避免假设版本号相同就兼容。
- 保持现有 `app.*` 导入路径，先以兼容视图交付；真正退役路径时按已有治理规则提供消费者迁移证据。
- 每任务一个可审阅提交，记录影响模块、行为差异、验证和回退方法。本文不代替用户的提交/推送指令。
- 代码回滚使用明确提交的反向变更或版本切换，避免覆盖现有未提交工作；回滚期间不得双重调用工具或模型。
- Registry/Dispatcher 回退由 Composition Root 显式选择旧适配，内部失败不自动换另一套后端。
- 有持久化变化时采用兼容迁移和旧记录读取；Checkpoint Schema 不兼容应拒绝恢复并提供原因，不能强行重解释旧状态。
- 内网真实来源不可用时允许显示失败或使用明确选择的演示 Profile，禁止静默混入模拟事实。

### 10.1 外部契约与过渡内部入口

| 类别 | 兼容策略 | 退出/变更要求 |
| --- | --- | --- |
| 公共 API、外部事件、持久化/结果读取 | 默认稳定，必要变更有版本和兼容读取 | 对消费方、已有数据和前端分别验收 |
| 已被外部使用的 Python 入口 | 先维护兼容，记录使用证据 | 提供替代入口和消费者迁移证据后再退役 |
| 内部转发、测试 patch、临时依赖查找 | 过渡维护，不作为新接口的永久设计约束 | 逐项转向 Port/Fake 和明确装配，达到退出条件后删除 |

在 MOD-003 建立兼容台账：入口/符号、所有者、当前消费者、替代 Port、迁移任务、目标检查点、退出条件和验证结果。P2 是收敛检查点，不代表不经审查强制删除全部旧入口。

从试点开始，新功能测试直接注入 Fake Dispatcher/Model/Store；旧 patch 测试仅作为过渡契约保留。删除某入口前必须确认生产内部消费者已迁移、必要的外部迁移证据齐备、旧测试已由新接口的行为测试覆盖、完整回归通过。测试变更不得掩盖真正的外部行为退化。

新 Runtime 不能为了维持旧 patch 方式反向导入 service 或 compatibility；兼容 Adapter 从外侧适配旧路径。保留旧 `TOOLS`/`TOOL_HANDLERS` 对象身份是阶段性约束，退出必须登记；无需让新接口永久暴露可变全局注册表。

## 11. 风险与对应验收

| 风险 | 控制方法 |
| --- | --- |
| 用目录搬迁掩盖依赖未解耦 | 在仓库外启动模块，并替换实际依赖验证调用方不改 |
| 新输入模型改变默认值/类型转换 | 逐工具比较 Schema 和运行语义；错误类型变化单独登记 |
| 兼容视图破坏对象身份和 patch | 保留现有身份/实时注入测试，先适配后退役 |
| 新旧注册表或 Playbook/Workflow 漂移 | 每类定义只有一个权威来源，其他视图生成或引用 |
| Dispatcher 与旧 Guard 双重计数 | 记录预算所有者，跨路径验证精确调用数 |
| 归一化 ToolResult 丢失证据语义 | 对照调用 ID、范围、时间、grain、来源及结论强度 |
| 类型拆分产生多个状态副本 | 阶段返回显式更新，运行状态单一所有者；并行前定义归约 |
| Skill 内容被当成授权或可执行代码 | 服务端 Policy 独立检查，依赖/资源清单受控 |
| 新版 Skill 改变正在执行任务 | 固定声明版本，旧版本保留到相关 Run 结束 |
| 恢复误复用过期或其他主体的数据 | 校验主体、版本、范围、新鲜度和已提交结果引用 |
| 测试只验证 Fake、真实语义不兼容 | 企业阶段使用脱敏接口夹具和版本化契约回放 |
| 抽象增加延迟和上下文负担 | 固定请求次数、Token、Runtime 与用户首答指标 |
| 企业任务被顺带激活 | 分开记录接口离线通过与真实环境通过，保留暂缓标识 |
| 纵向验证太晚造成批量返工 | A 后立即贯通 Ready/Loop，B 通过后才推广其余工具 |
| 每目录一包或共享文件互相覆盖 | 模块/制品分开映射，单一文件发布所有者，先组合安装验收 |
| 平台二进制依赖无法在内网安装 | 按 OS/CPU/Python 锁定依赖并在匹配环境验收 |
| 兼容层无限期膨胀 | 维护消费者/替代入口/退出条件，新测试使用 Ports |
| 超时被误认为已取消外部操作 | 区分停止等待、确认取消和未确定结果，拒绝迟到状态更新 |
| 小模型生成 SQL 或绕过工具清单 | 无 SQL 业务 Schema、服务端能力限制、伪造旧调用拒绝及查询计数为零；不以提示词或只读 SQL 白名单替代 |
| 为分层搬出 SQL 聚合而改变业务口径 | 保留可验证的聚合下推，逐项核对 Cpk、单位、grain、空值和舍入；Fake 与真实来源分别验收 |

## 13. 总体验收与建议启动点

完成主体解耦时，应能演示：

1. 一个新增查询 Tool 独立验收后注册进入系统，Agent Loop 无需修改。
2. 一个新 Skill 通过依赖检查后启用，核心 Runtime 无需修改。
3. Fake 数据与目标数据 Adapter 通过绑定切换，工具和证据代码不改。
4. Ready 和 Loop 对公共执行规则给出一致结果，Ready 不增加模型选工具轮次。
5. 制造范围、引用和结论强度继续受原有证据门约束。
6. 一个已提交步骤可在只读恢复场景复用，未确定/过期结果被正确处理。
7. 模块在仓库外逐块运行，并能重新组成完整 API 用户链路。
8. 已有质量门、兼容约束和冻结后的性能门通过；生产接入能力按实际验收单独声明。

建议施工主线为 `MOD-001 → MOD-002 → MOD-003`，随后实现一个工具、它的数据 Port 和最小 Dispatcher，立即贯通 Ready/Loop。纵向切片通过后才推广其余工具、完成 Runtime/模型服务收口。目录迁移围绕稳定边界推进；Skill/恢复按新增能力验收；公司侧可从首个通过隔离验收的制品开始搬迁。

### 13.1 数据访问边界（用户确认）

面向 Agent 的制造数据、知识和案例读取统一沿 `Agent / Skill / Workflow → Tool Dispatcher → Tool Handler → Data Port → Adapter → 数据源` 进入。Skill 组织场景和 Workflow，不直接执行 SQL；Tool 不要求由模型选择，Ready Workflow 仍可由服务端确定性调度。

会话、Checkpoint、知识上传/索引等应用内部写入使用 `Runtime / Memory / 知识管理用例 → Store 或 Repository Port → 数据库 Adapter`。这类内部保存不绕经模型工具系统。两条链路都要求 SQL、连接、事务和数据库方言留在 Adapter/Repository 中，核心 Runtime、Skill 和领域规则不直接写 SQL。

面向量化小模型，模型仅表达业务工具调用和受验证参数，不编写或提交可执行 SQL。旧 `query_manufacturing_data(sql)` 的移除与替代按第 5.9 节追踪；本次仅修订文档，当前运行代码尚未完成该限制。

公司侧以业务契约为稳定边界，实际选择只读数据库或报表/API 由服务端显式绑定；两种接入不要求同时实现，也不互为隐式故障回退。公司业务数据、应用自有存储和演示数据分别管理，按第 5.10 节渐进处理现有数据库入口；具体接入前提见第 9.4 节。

预计结构本身不能证明当前实现已经解耦。最终报告应逐项提供第 4.5 节证据和允许依赖清单：能替换哪种依赖、替换时修改了哪些文件、独立验收安装了哪些制品、原有行为是否保持。只有目录树或单测数量，不足以将该模块标为解耦完成。
